### 4.3 Automating the Claude Desktop recordings

**Spike 2.0 result (2026-11-14): R1 passes.** Claude Desktop 5.11492.5
(Electron, package `claude-desktop`, `/usr/lib/claude-desktop`) was
driven in Xvfb by `xdotool` 3.20160805 and recorded by x11grab. M1 ran
from the typed prompt to a drill-down inside the view, the host's side
pane and fullscreen; `demo:gif` made a 20 s, 1.09 MB GIF. Method:

| Step | How |
|---|---|
| Separate profile | `XDG_CONFIG_HOME=<dir>` gives Desktop its own `<dir>/Claude` (data, single-instance lock, `claude_desktop_config.json`); the owner's `~/.config/Claude` is untouched |
| Test data | That config lists only `ai-credits-analyzer` (`scripts/mcp-server.sh`) with `env` `HOME`, `USERPROFILE`, `XDG_CONFIG_HOME` on a `createFixtureHome` home and `AGENT_COST_ANALYZER_NOW` = `FIXTURE_NOW` |
| Sign-in | Once, by the owner, with the same `XDG_CONFIG_HOME` on the real desktop (email sign-in); the session survives a restart in Xvfb (the D-Bus keyring is reachable from Xvfb) |
| Launch | `Xvfb :93 -screen 0 1600x1000x24`, then `DISPLAY=:93 claude-desktop --ozone-platform=x11`; with no window manager the window opens at 1200x800 and `xdotool windowmove 0 0 windowsize 1600 1000` fits it |
| Mode | The profile opens in Code mode: click the Chat toggle once, collapse the sidebar; Ctrl+N opens a new chat |
| Prompt | `xdotool type --delay 60`, then Return |
| Wait and click | Poll a one-frame x11grab PNG, OpenCV `matchTemplate` (`TM_CCOEFF_NORMED`, threshold 0.9) against templates cut from earlier frames (Fullscreen, Always allow, stop button, a session row), click the match centre; "answer done" = the stop-button template gone |
| Permissions | Each tool asks once per profile. One mouse click on **Always allow** keeps it; the Ctrl+Shift+Enter shortcut needs a second, timed press |

Findings that shape 2.1 and 2.3:

- **Dates:** the model reads "this week" from today's date, not the
  server's fixed clock, and the fixture's data ends on 2026-10-30. M1's
  prompt becomes "What did my coding agents cost in October?" (15
  sessions, 21 turns, three providers); every M prompt names a period
  inside the fixture.
- **Privacy:** the new-chat screen shows "Welcome …, <owner's first
  name>" and the owner's recent artifacts; the device name appears next
  to the tool status. A take starts recording after the prompt is sent
  (D17); owner frame review (2.4) stays.
- **Allow prompts:** pre-approve every tool in the profile before final
  takes, so no prompt covers a view (D16).
- **Fullscreen:** the view's **Fullscreen** button and the host's expand
  icon both open a side pane; its expand icon then fills the window. The
  view's card stays 640 px wide at the left, the rest blank. Takes stop at
  the side pane (D18).
- **A turn row in fullscreen didn't open**; a likely cause is the
  `get_turn` permission prompt, which shows in the hidden chat.
  Pre-approval (above) should settle it; check in 2.1.
- **Remote debugging (R2) and the Electron fuses** were not checked; R1
  is enough.

| Route | How | For | Against |
|---|---|---|---|
| **R1 Simulated keyboard and mouse (recommended)** | Desktop in Xvfb (or X11 with `--ozone-platform=x11`); `xdotool` types the prompt and presses Enter; clicks inside a view go to coordinates found by template matching against screenshots; ffmpeg `x11grab` records | Only Desktop's public UI; no internals; any Electron build | Coordinate clicks break on layout changes; waits by screenshot polling; fixed window size and theme |
| R2 Remote debugging | Start Desktop with a remote-debugging port; drive it with Playwright `_electron` or CDP like the wdio suite | Precise element waits, clicks inside view frames | The app may block remote debugging (fuses); driving its internals may conflict with its terms; app updates break it |
| R3 Computer-use agent | An agent drives Desktop from screenshots | No scripting | Different every run, costs per take, poor demo pacing |

Constraints for any route:

- A signed-in account in a separate profile or account, as the Copilot
  suite's throwaway profile; the owner's chat list and account name never
  on screen. The privacy probe can't read Desktop's DOM under R1, so the
  owner reviews every frame.
- Each take spends a few messages on the owner's Claude plan, and the
  model's words differ between takes.
- Desktop updates itself and can't be pinned like VS Code
  (`vscode-version.mts`): record the Desktop version with each take.

## 5. Technique

Phase 1 (VS Code):

```
xvfb-run -a -s "-screen 0 1600x1000x24"   (WAYLAND_DISPLAY unset; fit-window.py sizes VS Code)
 └─ wdio (demo config)
     ├─ launcher: profile copy + seed + bridge   ← factored out of wdio.copilot.conf.mts (1.2)
     ├─ per scene: recorder.start(scene)  →  ffmpeg -f x11grab -i $DISPLAY … scene.mp4
     │             scene steps at demo pace (pointer overlay, typed text, beats)
     │             privacy probe over workbench + webview text
     │             stills: browser.saveScreenshot
     │             recorder.stop()  (sends "q", so the MP4 closes cleanly)
     └─ no release-evidence hooks, no git notes
npm run demo:gif   →  mp4 → palettegen/paletteuse GIF, size check, copy to docs/images/demo/
```

Spike 1.0 findings (2026-11-13, VS Code 1.146.0 under `xvfb-run`):

- **Frame.** wdio-vscode-service can't resize the window
  (`setWindowRect` fails: `Browser.getWindowForTarget` unknown), and
  without a window manager VS Code opens its first window at a fixed
  1200×800, centred; `window.newWindowDimensions`, a seeded `windowsState`
  in `storage.json` and `workbench.action.toggleFullScreen` don't change
  it. An Xvfb screen of exactly 1200×800 makes the window fill the frame.
  So the frame was 1200×800, not D5's 1440×900. Superseded 2026-11-14:
  the owner found 1200×800 cut the panel off and forced scrollbars, and
  accepted larger GIFs. Without a window manager any X client may resize
  a top-level window, so `scripts/demo/fit-window.py` (Xlib through
  `ctypes`) sizes VS Code to a 1600×1000 Xvfb screen in each demo config's
  `before` hook; GIFs stay at 1:1 (1600 px) with an 8 MB cap.
- **Recording.** ffmpeg `x11grab` started from inside the wdio worker
  (`DISPLAY` inherited, e.g. `:99`) records the workbench, quick pick,
  webview and status bar; 30 fps held at 1× speed (`ultrafast`, crf 18,
  about 50 KB/s); sending `q` closes the MP4 cleanly in about 0.2 s.
  `WAYLAND_DISPLAY` unset plus `--ozone-platform=x11` keeps the window in
  Xvfb.
- **Tools.** On this machine `ffprobe` on `PATH` is a firejail wrapper
  that can't see `/tmp`; call `/usr/bin/ffprobe` (and `/usr/bin/ffmpeg`)
  by absolute path, or take the path from `AICA_FFMPEG`/`AICA_FFPROBE`.
  `xdotool` is not installed (Phase 2 needs it).
- **Clutter to remove in the demo configs (1.3, 1.4).** The service starts
  VS Code with `--disable-extensions`, which raises an "All installed
  extensions are temporarily disabled" toast; `notifications.clearAll`
  right after start doesn't catch it, because it appears later: clear
  notifications at each scene's start, after the panel loads, or launch
  through `KeepExtensionsLauncher`. The default `ui-fixture` shows
  "Copilot Chat is disabled or not installed" in the panel and "AI
  Credits: setup needed" in the status bar; free scenes other than E1
  need a fixture where Copilot Chat counts as installed (the `copilot`
  launch's approach, built-in Copilot Chat enabled) and logging is on
  (1.6a).
- **Fonts.** The workbench UI renders in the system sans (Noto Sans) and
  the editor in DejaVu Sans Mono; both are legible at 1:1. Pin
  `editor.fontFamily` to `DejaVu Sans Mono` in the demo settings.

Phase 2 (Claude Desktop, route R1) reuses the recorder, the scene timeline
and `demo:gif` from Phase 1; only the driver differs:

```
xvfb-run -a -s "-screen 0 1600x1000x24"
 └─ demo:record:desktop
     ├─ Claude Desktop (separate profile, MCP server → fixture home + fixed clock)
     ├─ per scene: recorder.start(scene)          ← Phase 1 recorder
     │             xdotool types the prompt; waits by template match; clicks matched points
     │             recorder.stop()
     └─ Desktop version written next to the MP4
```

- **Recording.** Use ffmpeg `x11grab` on the Xvfb display that wdio's VS
  Code draws into. This captures everything VS Code draws, including quick
  picks, the status bar and webviews, and needs no CDP access to the
  Electron renderer. Settings: 30 fps, `libx264 -preset ultrafast -crf 18`
  while recording (so no frames drop), then re-encode. `--ozone-platform=x11`
  and an unset `WAYLAND_DISPLAY`, as in the release suite, keep the window
  inside Xvfb.
- **Demo pace.** A scene is data: a list of steps, each with an action and
  a beat (a pause after it). A runner plays the list. Tests keep their
  fast paths, so the waiting lives in the demos only. Phase 2 plays the
  same step lists through its `xdotool` driver.
- **Pointer overlay (Phase 1).** A `div` injected into the workbench
  document glides to the target's centre and ripples on click. For a
  target inside a webview, its position adds the offsets of the overlay
  iframe and the `#active-frame` iframe. Text goes in one character at a
  time, through `browser.keys`.
- **Scenes fail instead of recording garbage.** Each scene ends by
  asserting its end state (for example, the Savings view lists at least
  one row; in Phase 2, a template match of the expected view). A failed
  scene deletes its MP4.
- **Privacy probe (Phase 1).** At each scene's end it reads `innerText` of
  the workbench and every webview frame and matches it against forbidden
  strings from `DEMO_FORBIDDEN` (the owner's login, email, home path; set
  in the shell and never committed). A match fails the scene and deletes
  the video. `window.title` is fixed to `${rootName}`. The scenes never
  open the Accounts menu. Phase 2 has no DOM to read: the owner reviews
  every frame.
- **Real-Copilot scenes** reuse `sendToAgent`, so the model selection, the
  pre-send and in-flight checks and the AI Credits cap all apply
  unchanged. The model's words differ between takes. The owner reviews
  each take (1.10).
- **GIF.** `fps=12,scale=1200:-1:flags=lanczos,split[a][b];[a]palettegen=stats_mode=diff[p];[b][p]paletteuse=dither=bayer:bayer_scale=4:diff_mode=rectangle`.
  The script fails when a GIF exceeds 4 MB. Then lower the fps, trim, or
  publish that scene as an MP4 only.
- **Playwright GIFs** (app W1–W3, fake host F1–F3). Use Playwright
  `recordVideo` (WebM) in a demo-only Playwright project, then the same
  GIF step.

## 10. Delegation

### 10.1 Ground rules

- **Main session** (this conversation's agent): runs the spikes, writes
  each brief, reviews and merges each task branch, records the final
  free takes, edits the Gantt and this plan, and talks to the owner.
- **Subagents** do one task each, in their own worktree
  (`isolation: "worktree"`), on branch `claude/demo-<task id>`, with the
  model named in §6. They never commit to `main`, merge, or edit the
  Gantt or this plan.
- **The plan must be readable from a worktree.** This file is
  git-excluded, so a worktree doesn't have it. Until it is published
  (Phase 0 PR), each brief carries the needed plan text itself. After
  that, briefs point at `docs/plans/docs-refresh-and-demo-recordings.md`.
- **One wdio or Playwright run at a time.** VS Code instances and
  recordings compete for CPU and the X display. Every wdio, Playwright or
  ffmpeg run in a subagent goes through
  `flock "$XDG_RUNTIME_DIR/aica-demo.lock" <command>`, so agents can
  write code in parallel but run one at a time.
- **Subagents prove a scene, they don't make the final take.** A scene
  task runs its scene once to show the end-state assertion passes. Final
  takes come from one sequential run by the main session (1.10), or by
  the owner for paid scenes.

### 10.2 Brief template

Each brief is self-contained: the subagent knows only what it says.

```
  <task-specific commands>
  npm run headers:check && npm run lint && npm run typecheck && npm test

  flock "$XDG_RUNTIME_DIR/aica-demo.lock" <command>
Rules: SPDX header on new files (npm run headers:fix); no product code
  changes; no edits to the Gantt or the plan; doc edits keep the
  "Last changed" header current; if a §10.7 question comes up, stop and
  report it instead of choosing.

  output, anything left open.
```
